🛠️ Native Modding & Mixin Architecture

Horizon native mods are not sandboxed bytecodes; they are high-performance Rust mixin bundles that compile directly into the game's executable using horizon-mixins.

⚡ How Native Compilation Works

When the launcher compiles Horizon, it takes the upstream game source, applies all installed .hnmod bundles via horizon-mixins.exe apply to create a unified stage workspace, and runs cargo.exe build --profile fast -p horizon-client. This eliminates FFI and VM overhead: your mod runs at native CPU speed directly inside the engine loop.

Injection Types

Kind Description Use Case
HEAD Injected at the very start of the target method before any vanilla logic runs. Interception, tick updates, state recording, early cancellation.
RETURN Injected right before every return point or at function exit. Post-processing results, modifying return values.
BEFORE_CALL Injected right before a specific internal method call inside the function. Intercepting sound playback, packet dispatch, or entity spawning.
MODIFY_ARG Alters a specific argument passed into an internal function. Adjusting damage amounts, jump velocities, reach distances.
OVERWRITE Completely replaces the target function body. Major mechanic overhauls, custom rendering pipelines.

📄 Manifest Reference (horizon-mixin.toml)

Every native mod must provide a horizon-mixin.toml specifying its metadata, bundle dependencies, injected support modules, and function hooks.

[mod]
id = "my_custom_mod"
version = "0.1.0"
priority = 100

[compatibility]
horizon_revision = "66f3981f522b24c250b21523a70080965b940424"

# Optional Rust crate bundled directly with the mod (e.g. bevy_ecs)
[[crate]]
id = "ecs"
path = "ecs"

# Modules injected into the game's compilation unit
[[module]]
id = "runtime"
file = "crates/horizon-client/src/game.rs"
name = "my_mod_runtime"
visibility = "pub(crate)"
source = "runtime.rs"

# Hook injections into Game methods
[[injection]]
id = "player_tick"
kind = "HEAD"
target = "horizon_client::game::native_hooks::Game<'_>::native_player_tick"
helper = "player_tick.rs"
bindings = [
  { name = "game", ty = "&mut crate::game::Game<'_>", value = "&mut *self" },
]

⚡ Bevy ECS Architecture (bevy-horizon)

bevy-horizon brings Bevy's data-driven Entity Component System (ECS) to Minecraft Horizon. Game state is ingested each tick, processed across modular schedules and systems, and outgoing actions are dispatched via an Outbox command buffer.

1. HostBridge Ingestion

At each native_player_tick, the local player's coords, rotation, health, and nearby tracked mobs are synced into Bevy Components (Transform, PlayerBundle, LiveMob).

2. Schedule Execution

Bevy schedules (Update, FixedUpdate) run multithreaded systems with query filtering (e.g. Query<(&Transform, &OrbitingMob)>) to simulate physics, orbits, and triggers.

3. Outbox Command Dispatch

Systems emit high-level commands into an Outbox resource (TeleportMob, PlaceBlock, ActionBar, FlameParticle) which are executed back on Horizon's Game<'_> context.
